# documentation requirements

## Errortypes
If a struct embeds `ErrantlyError` its considered a type of error and therefore an `ErrorType`
Every errortype gets a comment which includes:
- when : when the error would normally be raised (ie. returned/paniced upon)
- example : and example of raising (ie. returned/paniced upon) that error type
- panics : true/false - if the error panics and terminates runtime

## Issue Interfaces

When an error option carries domain context (URL, bytes, file path, etc.), don't create wrapper functions in consumer packages. Instead, use the **Issue Interface** pattern.

### The pattern

1. **Define an Issue struct** — a small, focused struct that embeds `ErrantlyError` and carries ONE piece of domain context:

```go
// URLIssue carries a URL for errors that involve HTTP endpoints.
type URLIssue struct {
    URL     URLString
    ErrantlyError
}
```

2. **Create an option function** that type-asserts against the Issue and enriches the message:

```go
// WithURL attaches the target URL to an ErrantlyError's message.
func WithURL(url string) OptionerFn {
    return func(targets ...any) error {
        for _, target := range targets {
            if issue, ok := target.(*URLIssue); ok {
                issue.URL = url
                issue.SetMessage(
                    fmt.Sprintf("%s — url: %s", issue.GetMessage(), url),
                )
            }
        }
        return nil
    }
}
```

3. **Compose Issues into error types** via embedding:

```go
type NetworkTransportError struct {
    BytesIssue   // ← provides Bytes field + WithBytes option support
    URLIssue     // ← provides URL field + WithURL option support
    ErrantlyError
}
```

Because `NetworkTransportError` embeds both `URLIssue` and `BytesIssue`, both `E.WithURL(...)` and `E.WithBytes(...)` work on it automatically — the option function's type assertion succeeds through embedding.

### When to use

- An error type needs to carry optional context that enriches the message (URL, raw bytes, file path, etc.)
- Multiple error types share the same kind of context (e.g., several HTTP errors all carry a URL)
- You find yourself writing wrapper functions in consumer packages like `func WithURL(url URLString) OptionerFn { return E.WithURL(string(url)) }` — these are a sign that the Issue is missing or should be used directly

### Anti-pattern: consumer wrappers

```go
// DON'T — thin wrapper that just converts types:
func WithURL(url URLString) OptionerFn {
    return E.WithURL(string(url))
}
```

Instead, callers use the errantly option directly: `E.WithURL(string(url))`. The Issue struct and its option function live in errantly and carry all the context of what a "URL" means to that specific error domain.


## handlers

An `ErrantlyHandler` receives every error that is explicitly recorded. The
registry is package-level, so a recorder is opted into once at process start
rather than threaded through every `E.NewErrantlyError` call site.

```go
recorder, err := PostgresRecorder.NewPostGresHandler(PostgresRecorder.WithSystem("dispatch"))
if err != nil { ... }
if recorder != nil { errantly.RegisterHandler(recorder) }
```

- **`RegisterHandler` is additive and idempotent.** Registering the same handler
  twice is a no-op. Errors constructed *before* the call do not gain the handler;
  they are already built.
- **`Record()` is explicit, not automatic.** Constructing an error does not write
  anything. A caller that wants the error persisted calls `Record()` and gets the
  handler failures back as one error — a silent failure would look like success.
- **A nil recorder is safe.** `NewPostGresHandler` returns `(nil, nil)` when
  `PGSQL_URL` is blank, and `Record` on a nil recorder is a no-op, so a service
  with no database needs no nil check at the call site.

### the driver stays out of the core

`github.com/verikono/glocalize/packages/go/errantly` compiles **no** database driver. The recorder lives in `github.com/verikono/glocalize/packages/go/errantly/postgres`, which is the only package in the family that imports `github.com/lib/pq`. Importing errantly alone therefore never pulls a driver into a binary that does not need one.

### PostgresRecorder

Writes to the `ErrorRecord` table through `database/sql` and the standard `github.com/lib/pq` driver.

- **Connection is lazy and retried.** A database that is down at boot delays nothing: the constructor returns immediately, a background goroutine retries every 15 seconds, and each failure prints a warning to stderr.
- **`Record` on an unconnected recorder is a no-op**, not an error. The console already carries the warning, and failing here would turn a reporting problem into a second error at the call site.
- **Only `ErrorRecord` is supported.** The insert names that table's columns, so `WithTable` rejects any other name rather than writing to a table the statement cannot address.
- **`system` identifies the writer** (`WithSystem`), which is how a reader tells one service's errors from another's. `code` carries the meta level. A blank value is written as SQL `NULL`, not an empty string.
- **`Close` releases the pool.** The recorder owns the handle, so a caller that constructs one owns closing it.
